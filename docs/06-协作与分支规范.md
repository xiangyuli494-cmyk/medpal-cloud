# 协作与分支规范（3 人 · 队长 t1）

> 一句话：**`main` 只收 PR，1 人 approve 才合，只有队长 t1 能点 merge。**
> 这不是流程洁癖——评委问「你们怎么协作」时，你的回答应该是打开仓库指着 PR 列表，而不是描述。

## 1. 角色与 approve 矩阵

三人：**t1（队长）** · **t2** · **t3**。账号对照先填在这（后面 CODEOWNERS 要用）：

| 代号 | 姓名 | GitHub 账号 | lane |
| --- | --- | --- | --- |
| t1 | 队长 | `xiangyuli494-cmyk` | 底座与收口（`packages/core`、`contracts`、方案书、答辩） |
| t2 | 队员 | `suyouZJF` | 应用与评测（`apps/`、`eval/`）——数据、页面、文档这类可并行的活 |
| t3 | 队员 | `zincumyu` | 云与交付（`providers/`、`deploy/`、`Dockerfile`、CI）——真机联调、CCE/APIG、压测这些硬活 |
`CODEOWNERS` 已按这三个账号填好；两人都已有 **write** 权限，可以直接推分支、开 PR。
**难度分配**：硬活（真机联调、CCE/APIG、压测、CI）默认给 t3，碎活（评测集扩充、演示页、部署文档、素材）默认给 t2，
t1 不接实现任务——他的产出是契约、合并、方案书、答辩，这些一旦被实现任务挤掉，全队一起卡住。

**谁批谁**（关键是「不要自己批自己」）：

| PR 作者 | 谁能 approve | 谁 merge |
| --- | --- | --- |
| t1 | t2 **或** t3 | t1（自己点 merge） |
| t2 | t1 **或** t3 | t1 |
| t3 | t1 **或** t2 | t1 |

额外规则：

- 改 `contracts/trace/schema.json`、`docs/solution/`、`README.md` 的 PR **必须 t1 approve**（CODEOWNERS 会自动 @ 他）。
- **跨 lane 的 PR**（同时动了 `apps/` 和 `providers/`）需要两条 lane 的人各一个 approve，或者 t1 + 另一条 lane 各一个。
- 一个人在同一时刻只该有一个「等待 review」的 PR。三个人的队，review 队列比代码更稀缺。

## 2. 分支命名

| 前缀 | 用于 | 例子 |
| --- | --- | --- |
| `feat/` | 新功能、新端点 | `feat/C2-conflict-check` |
| `fix/` | 修 bug | `fix/B6-gaussdb-dsn` |
| `docs/` | 只改文档 | `docs/C4-solution-outline` |
| `chore/` | 依赖、CI、脚本 | `chore/ci-huawei-job` |

格式：`<前缀>/<任务编号>-<英文短横 slug>`。编号必须能在 [docs/05-任务看板.md](05-任务看板.md) 里查到。

**禁止**：直推 `main`、用个人名做分支（`yg-dev`）、一个分支塞三个任务。

## 3. commit 规范

```text
[C2] 加冲突检测步骤

同一 head+rel 出现不同 tail 时记一条 gap，而不是静默取第一条。
验收：pytest tests/test_conflict.py -q → 3 passed
```

- 标题：`[编号] 动词开头的一句话`，≤ 50 字；
- 正文写**为什么**，不写「更新了文件」；
- 一个 commit 一个意思，别把格式化混进功能改动（会让 diff 变成 800 行）。

## 4. PR 规则

1. 标题：`[C2] conflict_check 落地` —— 与 issue、分支、看板三处编号一致；
2. 正文用 [.github/pull_request_template.md](../.github/pull_request_template.md)，**验收输出必须贴真实结果**；
3. 规模 ≤ **400 行 diff**（`git diff --numstat` 相加），超了拆成两个 PR；
4. 一个 PR 只做一件事。顺手改的格式、顺手删的注释，另开 `chore/` PR；
5. 开 PR 即触发 CI（`.github/workflows/ci.yml` + `pr-check.yml`），红了自己修，别让别人等；
6. 提 PR 后 **24 小时内**必须有人 review；超时就在站会上点名；
7. Draft PR 可以用来提前要意见，但**不算交付**，不进看板。

## 5. 保护分支怎么设置（GitHub 点一遍，10 分钟）

仓库 → **Settings → Branches → Add branch protection rule**，Branch name pattern 填 `main`：

| 勾选项 | 值 | 为什么 |
| --- | --- | --- |
| Require a pull request before merging | ✅ | 直推直接消失 |
| └ Required approvals | **1** | 三个人的队，2 个会卡死 |
| └ Dismiss stale approvals when new commits are pushed | ✅ | 改了代码旧批准作废，防止「批完再偷改」 |
| └ Require review from Code Owners | ✗ 不开 | 账号已填真名，但首行 `*` 的 owner 是队长本人：他提 PR 时没法给自己 approve，一开就永久卡住。CODEOWNERS 只当「自动 @ 到对的人」的路由表，强制审批靠 §1 的人工矩阵 |
| └ Require approval of the most recent reviewable push | ✅ | 堵住「自己 push 完自己合」 |
| Require status checks to pass | ✅ 选 `test (3.11)`、`test (3.12)`、`meta`、`size` | CI 不绿合不了 |
| └ Require branches to be up to date | ✅ | 逼你 rebase 到最新 main 再合，减少「合完就红」 |
| Require conversation resolution before merging | ✅ | 评论没解决不能合 |
| Do not allow bypassing the above settings | ✅ | 管理员也不能绕，包括你自己 |
| Restrict who can push to matching branches | ✅ 只留 t1 的账号 | 队长是唯一 merge 人 |

另外 **Settings → General → Pull Requests**：关掉 Merge commits 和 Rebase merging，**只留 Squash merging**，勾上 **Automatically delete head branches**。
历史保持一条任务一个提交，回头看 `git log --oneline` 就是一张进度表。

> 如果队长 t1 不是仓库 owner：先在 Settings → Collaborators 把 t1 加成 **Admin**，否则他连保护规则的开关都看不到，也没法点 merge。

**顺序别搞反**：先把首个基线提交 push 上去，**再**开保护。反了的话你自己都推不上去（`enforce_admins` 连管理员一起挡）。
要临时拆掉：`gh api -X DELETE repos/<OWNER>/<REPO>/branches/main/protection`（没装 gh 就用 `curl -X DELETE -H "Authorization: Bearer $GITHUB_TOKEN" https://api.github.com/repos/<OWNER>/<REPO>/branches/main/protection`）。

一键设置（把表里那些勾选项直接用 API 打上，省得三个人点出三种配置）：

~~~bash
bash scripts/setup-branch-protection.sh                 # 默认：PR + 1 approve + CI 绿 + 禁直推/强推
bash scripts/setup-branch-protection.sh --restrict      # 再加「只有队长能 push」
bash scripts/setup-branch-protection.sh --restrict --codeowner   # 真账号填好后再加这条
~~~

脚本不依赖 `gh`：按 `$GITHUB_TOKEN` → `gh auth token` → `git credential`（GCM 缓存）的顺序取 token，取到一个就能跑。
打完后它会 GET 回来把实际生效的开关打印一遍——**以打印结果为准，不以勾选框为准**。

### 5.1 改工作流文件时怎么绕过保护（唯一的例外）

`enforce_admins=true` 意味着队长直推也会被拒。改 `.github/workflows/`、`scripts/setup-branch-protection.sh`
这类**保护规则自己要读的文件**时，按这个顺序做，一步不能省：

1. 摘保护：`curl -X DELETE -H "Authorization: Bearer $TOKEN" https://api.github.com/repos/<OWNER>/<REPO>/branches/main/protection`
2. 直推（此时 `main` 裸奔，所以第 3 步必须紧接着做）；
3. 立刻打回：`bash scripts/setup-branch-protection.sh`；
4. 提交信息里留一行 `protection-off: <原因>`，站会上说明。

窗口只到这一次 push 结束——**不许隔夜**。业务代码永远走 PR，这条只给工作流与保护脚本本身。

> 硬性排除：**合并 PR 不属于这条例外**。手上有 approve 就正常走 merge，没有就等。
> 用 DELETE protection + API merge 去合一个没拿到 approve 的 PR，视为流程违规；
> 不因为「反正是我自己的分支」「反正改的都是文档」而例外。2026-11-04 发生过一次，见 §5.3。

### 5.2 合并门禁：一律走脚本，别手点

合并前先跑：

```bash
bash scripts/merge_pr.sh <PR号> --dry-run   # 只看能不能合
bash scripts/merge_pr.sh <PR号>             # 真合并（squash）
```

判定规则写死在脚本里，不靠记忆：

| PR 作者 | head 上需要的 APPROVED | 其他条件 |
| --- | --- | --- |
| 不是队长 | >= 1（不能自己批自己） | 全部 check-run 为 success / skipped / neutral |
| 队长自己 | >= 2（t2、t3 各一个） | 同上 |

- 只认 **head 提交** 上的 approve；rebase / force-push 后旧 approve 作废，这与 `dismiss_stale_reviews` 一致；
- 脚本**不提供 --force**。要绕过只能手写 curl，那等于自证违规：站会说明 + PR 里留追认记录；
- 合并方式固定 squash，与仓库设置一致；脚本失败时退出码 3，并打印缺谁、缺什么。

### 5.3 事故记录：2026-11-04 三次绕过 review 的合并

| PR | 内容 | 合并时 head 上的 approve | 怎么合的 |
| --- | --- | --- | --- |
| #43 | C1 契约冻结 | 0（原两个 approve 被 force-push dismiss） | DELETE protection -> API merge |
| #48 | C2 冲突步 | 0 | 同上 |
| #49 | C4 方案书骨架 | 0 | 同上 |

- 三笔都没在提交信息里留 `protection-off:`，违反 §5.1 第 4 步；
- 补救：#43 / #48 / #49 各留评论请 t2、t3 复审并回「追认」或「建议 revert」，不追认的按 §8 revert；
- 制度补救：§5.2 的脚本门禁，此后合并只走脚本。

> `--restrict` 依赖分支保护的 *Restrict who can push*：**只有 organization 仓库支持**（个人仓库 API 直接回 422 `Only organization repositories can have users and team restrictions`，脚本会自动退回不加白名单并提示）。
> 用不了就走 fork 流程——t2/t3 只有只读权限，从自己的 fork 提 PR，仓库里只有队长能按 merge，效果一样，代价是每天多一条 `git remote add upstream`。

## 6. 同步与冲突

- 每天开工第一件事：`git switch main && git pull --rebase`；
- 分支落后就 `git rebase main`，**rebase 会作废旧 approve**（这是设计，不是 bug），要再要一次；
- 冲突 30 分钟没解完，站会上喊人一起看，别一个人硬啃两小时；
- 绝不 `git push --force` 到 `main`，也尽量别 force 到别人正在 review 的分支。

## 7. 每日节奏（配合 docs/04 §9）

| 时间 | 动作 |
| --- | --- |
| 每天开工 | rebase 到最新 main，看板上把自己的任务挪到 Doing |
| **20:00** | 当天要合的 PR 必须开出来（Freeze） |
| **21:00 站会 15 分钟** | 每人 2 分钟：昨天合了什么（贴 PR 号）/ 今天开什么 PR / 卡在哪；然后集体清 review 队列 |
| 站会结束 | 当天 PR 当天合；合不掉的写明「等谁、等什么」 |

## 8. 回滚

- 合坏了：`git revert <sha>` → 开反向 PR → 同样走 approve，不 reset `main`；
- 线上（云上）出问题：先回滚镜像 tag，再排查，别在线上改代码；
- 冻结期（11/22 之后）只接受 `fix/` 分支，标题前缀 `[hotfix]`。

## 9. 允许的例外（就这两条）

1. `docs-only` 的错别字 PR 可以 30 分钟内合，但仍需 1 个 approve（值班人给）；
2. 冻结期后的 hotfix 可以从 `v0.9` tag 切分支，但仍要 PR + approve + CI 绿。

**没有例外的**：赶时间直推 main、口头同意代替 approve、自己批自己的 PR（GitHub 也不让你批）。

## 10. 贴墙清单

**开 PR 前**
- [ ] `make pr` 本地通过（lint + 边界 + 禁用语 + test，约 20 秒）
- [ ] 分支从最新 `main` 切出，名字合规
- [ ] diff ≤ 400 行，只做一件任务
- [ ] 标题带编号，正文填了验收命令与真实输出

**点 merge 前（队长）**
- [ ] CI 全绿，没有 pending
- [ ] 已有 1 个 approve，且不是作者自己
- [ ] 评论全部 resolved
- [ ] 已 rebase 到最新 `main`
