### 3.1 合并闸门（本周就生效，不是等上云）

每个任务 = 一个 issue + 一个分支 + 一个 PR。**`main` 保护，直推一律拒绝**，队长也不例外。

| 规则 | 具体 |
| --- | --- |
| 分支 | `feat/C2-conflict-check`、`fix/B6-gaussdb-dsn`、`docs/C4-outline`；从最新 `main` 切 |
| PR 标题 | `[C2] conflict_check 落地` —— 编号必须对得上 docs/05 |
| 规模 | ≤ 400 行 diff，一个 PR 只做一件任务；超了拆 |
| 门禁 | CI 四个检查全绿（ruff / 边界 / 禁用语 / pytest 3.11+3.12）+ PR 元信息检查 |
| approve | **至少 1 人 approve**，且必须是另一条 lane 的人（见 docs/06 §5 矩阵） |
| merge | 只有队长 **t1** 点合并；t1 自己的 PR 由 t2 或 t3 approve 后他自己合 |
| 时限 | 提 PR 后 **24 小时内**必须有人 review，最迟次日站会前处理 |
| 回滚 | 出事用 `git revert <sha>` 反向 PR，不 reset `main`，不 force push |

代价要算进日历：**每个任务多 0.3 天**（提 PR + 等 review + 改）。所以下面的日期已经按「做完即提 PR」排，不是按「代码写完就完事」排。

## 5. 验收标准怎么定（统一口径）

每条任务的验收只有三种形态，别的都不算完成：

1. **命令 + 期望输出**：贴命令，贴真实输出（不是「应该可以」）。例：
   `python eval/run_eval.py` → `dept_acc=1.0 ... (n=60)`
2. **文件 + 具体内容**：文件存在，且打开能看到明确条目（不是空壳、不是 TODO）。
3. **数字指标**：带阈值的数，例如「P95 < 8s」「错误率 0」「≥30 条」。

三种都不是的（「优化一下」「完善文档」），不许进看板。

## 9. 每日节奏

- **21:00 站会 15 分钟**，三个问题：昨天交付了什么（贴验收命令输出）、今天交付什么、卡在哪。
- 任务粒度 ≤ 1 天；**没有验收标准的任务不进看板**（见 docs/05）。
- **20:00 冻结**：当天要合的 PR 必须在这之前开出来，21:00 站会里当场 review + 合并；
- 分支：`main` 保护，一人一分支，**1 人 approve 才能合**，只有队长 t1 能点 merge（细则见 docs/06）；
- review 带宽：每人每天最多 review 2 个 PR，超过就让对方拆小；别把 review 堆到周日。
- 每天的合并必须在离线状态通过 `bash tools/dev.sh all` —— 这是唯一不允许商量的规矩。
