# 复用清单：从 medpal 抽了什么、为什么这么抽

## 1. 为什么不直接在 medpal 里改

- medpal 是「院内智慧陪诊终端」，主线压在赛题3（ModelEngine Nexent 智能体），
  赛题3 结题时间在赛题1 之后，**动它就是拿两条线一起冒险**。
- 赛题1 需要一个「唯一提交入口」的仓：评委 clone 下来就得能跑，不该看见另一条赛道的
  `agent/skills`、Nexent 配置、设备固件与原型页。
- 所以：**新开一仓，底座复制而非搬走，medpal 打 tag 归档、一行不改。**

| 来源（medpal） | 去向（本仓） | 规模 | 判断 |

`db_path()` 改名 `db_file()` 以免和 `connect()` 的参数撞名。逻辑一行没动。

## 3. 没抽的部分（留在 medpal）

| 内容 | 原因 |
| --- | --- |
| `agent/skills/`（246 行） | Nexent 专有编排，赛题1 用不上 |
| 赛题3 方案书、charter、预算表 | 另一条赛道 |
| `server.py` 的 10 个 `@mcp.tool` 语义 | MCP 暴露方式与赛题1 的 HTTP 形态不同，语义重写为 pipeline |
| `backend/domain/triage` | 分诊业务逻辑，属应用层，不属底座 |
| `frontend/user-app`（2437 行） | 面向患者的产品壳 |
| `demo/`、`docs/plan|specs|adr`（1337 行） | 另一条赛道的文档与原型 |
| `device/`, `firmware/`, `hardware/` | 终端硬件 |

## 4. 三条判据（以后想往 core 塞东西，先过这三关）

1. **与赛题无关**：换个赛题还能用。
2. **与行业无关**：换个行业只换 `data/lexicon/`.
3. **与厂商无关**：换个云只换 `providers/`.

三条有一条不满足，就放在 `apps/` 而不是 `packages/core/`。

## 5. 拆仓触发条件（什么时候该再拆）

- core 被第二个应用（赛题2 工具、院内其他系统）真实引用；
- core 需要独立发版号；
- 出现第三份 provider；
- 团队里有人开始抱怨「改 core 要跑整个应用的 CI」。

四条出现两条，就把 `packages/core` 独立成仓，本仓改为依赖它。
**现在不拆**：一个仓、一个 CI、一次提交，对比赛周期最省事。
